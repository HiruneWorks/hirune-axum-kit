# Deployment

This directory owns runtime wiring and operator commands. Image build files live
in `compose/`; secret settings live in ignored `.envs/.<environment>/` directories.
The initial deployment uses an externally provisioned PostgreSQL database and
SMTP server. Database backups, TLS termination, and provider configuration are
deployment responsibilities.

1. Build and publish an application image with `compose/production/app/Dockerfile`
   and the repository root as context. Publishing is an explicit operator action.
2. Copy `production.env.example` to `production.env`; set an immutable image tag
   or digest, unique COMPOSE_PROJECT_NAME, and API_PORT.
3. Copy the production examples under `.envs/.example/production/` into
   `.envs/.production/`. Set HTTPS origins, runtime database credentials, SMTP, and
   independently generated encryption/rate-limit keys. Put the schema-owner URL
   only in `migration.env`; put the restricted maintenance URL in `maintenance.env`.
4. From this directory run `just check production`, then `just up production`.
   The latter runs migrations before starting/replacing API and worker.
5. Configure the host TLS proxy and readiness probe, verify mail/provider behavior,
   and arrange `just cleanup production` through the deployment scheduler.

A staging environment uses its own selector, project name, ports, database, and
`.envs/.<environment>/` directory. Production APP_ENV also applies to HTTPS staging.
Do not share authority tables or secret keys between unrelated environments.
The API binds to host loopback; configure a host reverse proxy and explicit proxy
trust before accepting public traffic. Workers can scale independently. Multiple
API replicas need deployment-level routing/port allocation; this single-host
example is not a load-balancer implementation.

`just down` preserves database data because this Compose project does not own the
database. Cleanup and retry operations are explicit. No deployment, image push,
external messages, or scheduler changes occur when running local checks.

## SMTP trust

Production requires `SMTP_STARTTLS=true`. Publicly trusted SMTP certificates use
the transport's normal trust store. For a private SMTP CA, set the optional
`SMTP_CA_CERTIFICATE` to the PEM CA certificate path inside the container, such
as `/certificates/smtp-ca.crt`. Add a read-only certificate mount to each API,
worker, manage, and maintenance container using that setting; every application
bootstrap constructs the mail transport. The default deployment Compose does
not add this mount automatically. The file must be readable by application user
10001; only the public CA certificate is needed, not its private key.

An empty or omitted setting uses the normal trust store. An unreadable or invalid
certificate fails startup, and a custom certificate requires STARTTLS. Adding a
CA preserves certificate-chain and `SMTP_HOST` hostname verification; it does not
disable either. Keep production certificates and mounts separate from the
ephemeral certificates generated by `just test-production`.

## Database roles and maintenance

Provision three database roles. Migration owns schema changes. Runtime has only
the required application privileges and migration-history SELECT; audit events
allow insertion and reading, with no update or delete. Maintenance has the runtime
permissions needed for authentication/job/file cleanup plus audit deletion, without
schema ownership or DDL. Environment separation is wiring, so verify the actual
database grants as part of deployment acceptance.

API, worker, and the ordinary `manage` service read `app.env`. The `maintenance`
service reads `app.env` followed by `maintenance.env`, overriding `DATABASE_URL`
only for explicit cleanup. `just cleanup production` invokes that service. Avoid
running audit cleanup through the runtime `manage` service or giving runtime
processes broader permissions to make it succeed.

Defaults retain succeeded jobs for 30 days, failed jobs for 90 days, and audit
events for 180 days. Set `SUCCEEDED_JOB_RETENTION_DAYS`, `FAILED_JOB_RETENTION_DAYS`,
and `AUDIT_RETENTION_DAYS` in `app.env`; each supports 1 through 36500 days. Deleting
a failed job removes its attempt history and retry ability. Bounded cleanup may
need repeated runs to clear a backlog.

The optional [systemd service](systemd/hirune-maintenance.service) and
[timer](systemd/hirune-maintenance.timer) run cleanup followed by `repair-search`
every five minutes, with up to 30 seconds of randomized delay. The templates use
`/opt/hirune/deploy`, `/usr/bin/docker`, and `production.env`; adapt these paths
and the environment selector before installing them. The timer is persistent and
can run after a missed scheduled execution. Neither local checks nor deployment
startup installs or enables these host units.

Grant global administrator status with
`just manage production set-administrator <uuid> true` only after the account is
active, verified, and enrolled in TOTP. Use `false` to demote it. The command
invalidates existing credentials and audits a changed role. Restrict operator
access to management commands; there is no public administrator-management API.

Optional file storage uses an externally provisioned private S3-compatible
SeaweedFS gateway and bucket. The master, filer, volume servers, and gateway admin
interfaces must stay on private infrastructure. Configure production credentials
with bucket-limited read/write/list access; provisioning uses a separate operator
credential when bucket/index creation is not permitted to runtime credentials.
API/worker startup does not create buckets or search indexes.

Meilisearch is an optional private derived index. Provision the file index using
`manage initialize-integrations` with appropriate operator permissions, then use
an index-limited server key. Never send the master/runtime key to browsers.
Schedule `manage repair-search` as well as `manage cleanup`; file deletion and
indexing jobs require a running worker. Back up PostgreSQL and file originals;
rebuild the search index from DB metadata when needed.

The container has a 512 MiB temporary filesystem for bounded upload spooling.
Default four concurrent 100 MiB uploads fit within it. Increasing file size or
transfer concurrency requires increasing temporary capacity or mounting a
dedicated temporary directory and setting `FILE_TEMPORARY_DIRECTORY`. The private
temporary directory must not be a served or executable application path.
